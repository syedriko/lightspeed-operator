# TLS

The operator manages TLS certificates for all inter-component communication and external endpoints.

## Behavioral Rules

### Certificate Sources

1. The operator supports two TLS certificate sources for the backend API endpoint: OpenShift service-ca (default) and user-provided custom certificates.
2. When no custom TLS is configured, the operator annotates the backend Service with `service.beta.openshift.io/serving-cert-secret-name: lightspeed-tls`. The service-ca operator then generates and manages the certificate automatically.
3. When `spec.ols.tlsConfig.keyCertSecretRef` is set, the operator uses the referenced Secret containing tls.crt, tls.key, and optionally ca.crt. The service-ca annotation is omitted from the Service.
4. PostgreSQL TLS certificates are always generated by the service-ca operator (not configurable by the user). The PostgreSQL config file references `/etc/certs/tls.crt`, `/etc/certs/tls.key`, and the service-ca CA at `/etc/certs/cm-olspostgresca/service-ca.crt`.
5. Console UI TLS certificates are always generated by the service-ca operator via the `lightspeed-console-plugin-cert` Secret.
6. OTEL Collector TLS certificates are always generated by the service-ca operator via the `lightspeed-otel-collector-cert` Secret (serving cert for OTLP gRPC/HTTP, `postgres_admin`, and HTTPS metrics via `https_metrics`).
7. Standalone MCP TLS certificates are generated by service-ca via `openshift-mcp-server-tls` when introspection is enabled. MCP reads the serving-cert paths from its TOML configuration; see [ocpmcp.md](ocpmcp.md).

### Certificate Mounting

1. Backend TLS certificates (custom or service-ca) are mounted at `/etc/certs/lightspeed-tls/` in the API container. Both tls.crt and tls.key are read from this path.
2. The TLS secret must contain at minimum `tls.key` and `tls.crt` keys. For service-ca secrets, the operator relies on the secret being created asynchronously by the service-ca operator.
3. PostgreSQL CA certificates are mounted from the `openshift-service-ca.crt` ConfigMap into the backend container at `/etc/certs/postgres-ca/` for verifying PostgreSQL connections. The SSL mode is fixed to `require`.
4. The OpenShift root CA (`kube-root-ca.crt`) is always mounted at `/etc/certs/ols-additional-ca/` in the backend container.
5. Appserver copies the OpenShift service-ca bundle (`openshift-service-ca.crt` / `service-ca.crt`) into classic client-only Secret `lightspeed-otel-client-ca` (`otel-ca.crt`), mounts it as `/etc/certs/otel-collector-ca/service-ca.crt`, and adds the path to `extra_ca` in `olsconfig.yaml`. The app-server also sets `OTEL_EXPORTER_OTLP_CERTIFICATE` to that path so the OTLP/gRPC exporter trusts the collector (gRPC does not use the certifi/`extra_ca` store). Agentic trust uses a distinct Secret, `lightspeed-agentic-otel-ca`.
6. When introspection is enabled, appserver copies the same cluster service-ca PEM into classic client-only Secret `lightspeed-mcp-client-ca` (`mcp-ca.crt`), projects that key as `/etc/certs/openshift-mcp-server-ca/service-ca.crt`, and adds the path to `extra_ca` so lightspeed-service can verify TLS to the standalone MCP Service on `:8443`. There is no dedicated inject-cabundle MCP client CA ConfigMap; the separate public backend-trust snapshot is described below.
7. When OKP is enabled (`!byokRAGOnly`), appserver copies the cluster service-ca PEM into classic client-only Secret `lightspeed-rhokp-client-ca` (`rhokp-ca.crt`), mounts it as `/etc/certs/rhokp-ca/service-ca.crt`, and adds the path to `extra_ca` so lightspeed-service can verify TLS to the standalone RHOKP Service on `:8443`.
8. Separate agentic CA Secrets (`lightspeed-agentic-otel-ca`, `lightspeed-agentic-mcp-ca`, `lightspeed-agentic-rhokp-ca`) are reconciled only when the agentic gate is Enabled, with MCP/RHOKP also subject to their operand toggles. Disabled/Unknown gates preserve existing agentic Secrets without reads, writes, or deletes. See [agentic-sandbox-profile.md](agentic-sandbox-profile.md).

### Additional CA Certificates

 1. If `spec.ols.additionalCAConfigMapRef` is set, the operator mounts the referenced ConfigMap in the backend container at `/etc/certs/ols-user-ca/` and each certificate file path is added to the `extra_ca` list in the OLS config.
 2. If `spec.ols.proxyConfig.proxyCACertificate` is set, the referenced ConfigMap key is mounted in the backend container at `/etc/certs/proxy-ca/`. The key defaults to `proxy-ca.crt` if not specified via `spec.ols.proxyConfig.proxyCACertificate.key`.

### MCP Toolset Backend CA Bundles

1. OSSM/NetObserv explicit backend trust uses typed `caBundleRef`, selecting exactly one local ConfigMap or Secret and an explicit name/key. See [crd-api.md](crd-api.md#toolset-ca-bundle-reference).
2. References resolve in the MCP operand namespace and remain user-owned. The operator strictly validates certificate-only X.509 PEM, canonicalizes it and copies only selected public certificates into operator-owned `openshift-mcp-server-trust`. Selected snapshot keys project read-only (0444) as `/etc/mcp-server/toolset-ca/{ossm,netobserv}/ca.crt`, mapped to each toolset's `certificate_authority`. MCP never projects live user sources or unselected keys/private material.
3. Missing sources/keys or invalid bundles fail clearly before publication/rollout, retaining the last validated snapshot and runtime configuration. Phase 2 revalidates sources and requires persisted Phase 1 snapshot data/hash to match before deployment generation. No insecure fallback is added.
4. Valid canonical content or reference-identity changes trigger MCP rollout using `ols.openshift.io/mcp-trust-hash`. Removal/deselection drops obsolete mounts/settings/tracking but never deletes user sources, including during disable/finalization. Creation/recovery/deletion also enqueue validation. Reserved runtime/trust/legacy CA ConfigMaps and serving TLS Secret cannot be selected; runtime/trust/legacy ConfigMap output collisions are ownership-guarded even after references are removed. Serving-Secret cleanup checks OLSConfig ownership or the originating OLSConfig-owned Service's matching UID before that Service is removed; unowned objects are preserved.
5. The operator accepts/generates only verified HTTPS configuration for OSSM and NetObserv; no `insecure` field is exposed. Actual local pinned-image OSSM/NetObserv HTTPS calls passed via singular custom CA files with that root absent from shared trust; generic mock responses do not prove real service semantics or authorization. The separate [full-manager live run](ocpmcp.md#full-manager-live-cluster-verification) verifies public selected-key projection/checksums, NetObserv baseline/override paths and CA watch rollouts; real OSSM/NetObserv service semantics and authorization remain [PLANNED: OLS-2715]. Explicit endpoints require `caBundleRef`. NetObserv service-based endpoints use an explicit bundle override or the validated cluster service CA from `openshift-service-ca.crt` / `service-ca.crt` in the operand namespace, mounted into MCP with an operator-generated path. Implicit service-CA changes must also validate and trigger MCP rollout. Do not rely on upstream opportunistic file discovery or fall back to insecure verification on errors.
6. These are outbound toolset-backend CAs, separate from MCP serving TLS, app-server/agentic MCP-client CA Secrets, and global OAuth trust. They do not extend unsupported vendor trust fields. Shared observability endpoint/trust contracts are specified below, with scoped local shipped-image passes in [runtime verification](ocpmcp.md#runtime-verification); other clients retain their documented upstream-specific behavior.

### Observability Logs and Traces Transport

1. Logs/traces static endpoints must be HTTPS; discovery is Route-based only, and insecure verification is not exposed. Reject service-DNS discovery selection rather than allow pinned upstream HTTP modes. There is no silent HTTP fallback.
2. Route HTTPS construction does not prove certificate trust. Shared vendor clients have no per-toolset CA path; their system/REST/service-CA trust behavior is inventoried in [config-generation.md](../how/config-generation.md#shared-observability-transport). Provision custom and cluster trust through the shared MCP-process contract below, not through nonexistent vendor per-toolset CA paths or OSSM/NetObserv-specific references.
3. Metrics endpoints also require verified HTTPS; no insecure option is exposed. Existing OLS Thanos/Alertmanager defaults remain HTTPS. Use shared process trust below for their system/custom/cluster CA validation. These transport policies do not alter authentication, compatibility filters or caller authorization.

### Shared MCP Process Trust

1. Managed MCP baseline trust preserves image/system roots and adds the validated cluster service-CA bundle. `spec.ols.mcpKubeServerConfig.caBundleRefs` supplies user bundles merged into that baseline; omitted/empty retains the baseline unchanged. See [reference API](crd-api.md#shared-mcp-ca-bundles).
2. Resolve each ConfigMap-or-Secret entry by explicit local name/key; validate and snapshot canonical public certificate PEM. Project only snapshot service/custom keys read-only at `/etc/mcp-server/ca`. Set `SSL_CERT_DIR=/etc/ssl/certs:/etc/pki/tls/certs:/etc/mcp-server/ca`, leave `SSL_CERT_FILE` unset and preserve default image certificate files/directories. Missing/invalid sources are clear errors, never a verification fallback.
3. This is process-shared trust for clients using system roots, including observability backend clients. It is not endpoint isolation or universal trust across every toolset. Preserve the singular OSSM/NetObserv client-specific CA settings and describe their actual root-pool composition.
4. Baseline service CA is always consumed/tracked while MCP is enabled, independently of NetObserv and even with empty selection. CA watchers queue reconciliation before MCP rollout and union existing shared-source consumers. Valid changes/removal roll by content/reference-identity hash; invalid updates retain the last validated snapshot and suppress roll. Removing user refs never removes baseline roots or deletes sources; disabled MCP-only refs ignore stale annotations.
5. Operator generation/lifecycle tests pass in full `make test` with default Kubernetes 1.27.1 envtest; fresh-process operator-toolchain tests are separate evidence. The exact pinned RHEL/FIPS image now passed actual serializer-generated static Prometheus/Loki/Tempo HTTPS calls with shared custom trust and unrelated populated REST CAData. All three reject unknown CA and wrong hostname in six cases before HTTP (zero backend requests). First-harness actual Prometheus calls accept shared synthetic service/custom roots and a REST CAData-only root; Alertmanager accepts the shared service root. Removing/rotating custom roots and restarting accepts the new leaf and rejects removed/old roots as expected, with no hot-reload claim. Inspection confirms the exact SSL_CERT_DIR in rule 2, SSL_CERT_FILE unset, image bundle's 146 certificates retained and no image certificate paths overmounted; external public-root HTTPS was not exercised. Actual namespace Python HTTPS metric query returned 2715 with custom roots; removal/rotation rejected TLS before additional backend HTTP, source updates rolled MCP, and real Service CA-only baseline trust succeeded. Bounded real Kubernetes caller Pod access/RBAC and policy denials also passed. Local-dev operator ServiceMonitor/metrics reader reconciliation was skipped; not production-deployment or hot-reload proof. ### TLS Security Profiles

 1. If `spec.ols.tlsSecurityProfile` is set, the operator applies the specified OpenShift TLS profile (minimum TLS version, cipher suites) to the backend API endpoints.
 2. If no TLS security profile is set, the operator falls back to the cluster API server's TLS profile, retrieved via the `config.openshift.io/v1` APIServer resource.
 3. Per-provider TLS security profiles can be configured via `spec.llm.providers[].tlsSecurityProfile` for outgoing connections to LLM providers.
 4. The operator's own metrics endpoint TLS profile follows the same logic as the backend: CR-specified profile, or fallback to the cluster API server's profile.

### Certificate Rotation

 1. Service-ca certificates are automatically rotated by the service-ca operator. The operator's watchers detect the Secret data change and trigger a deployment rolling restart via the `ols.openshift.io/force-reload` pod template annotation.
 2. Custom certificate rotation requires the user to update the referenced Secret. The operator detects the data change via the watcher and triggers a rolling restart using the same annotation mechanism.
 3. OTEL, MCP, and RHOKP serving-cert rotation invokes three independent watcher targets: operand restart, app-server restart, and handoff ConfigMap touch. MCP/RHOKP watches are enabled only while their operands are enabled.
 4. `RestartAppServer` refreshes applicable client CA Secrets from `openshift-service-ca.crt`, then rolls the app-server. Refresh failure skips the roll; it never directly touches the handoff.
 5. The separate `TouchAgenticConfiguration` callback runs only when the agentic gate is Enabled, including after earlier restart errors. Thus refresh failure does not suppress that callback. Service-ca bundle changes restart app-server and PostgreSQL and, while MCP is enabled, enqueue MCP CA validation before any MCP rollout, without a direct handoff touch. See [agentic-sandbox-profile.md](agentic-sandbox-profile.md).

### Agentic provider-egress handoff [PLANNED: new classic-operator ticket]

 1. The classic operator MUST reuse `spec.ols.tlsSecurityProfile` and `spec.ols.additionalCAConfigMapRef` for agentic sandbox provider egress. It MUST NOT add a TLS or CA surface to `AgenticOLSConfig`.
 2. The operator MUST publish the resolved profile type, minimum TLS version, and cipher-suite list as strings in the existing `lightspeed-agentic-configuration` ConfigMap under `tls-profile`, `tls-min-version`, and `tls-cipher-suites`. The cipher list is serialized as a JSON array.
 3. The operator MUST publish only the referenced additional CA ConfigMap name under `additional-ca-configmap`; certificate data MUST NOT be copied into the handoff ConfigMap.
 4. Existing operator-managed client CA Secret references remain `otel-ca-secret`, `mcp-ca-secret`, and `rhokp-ca-secret`. The operator owns Secret contents and publishes names only.
 5. Changes to resolved TLS values or referenced object names MUST update the handoff ConfigMap. Existing source watches and Secret refresh behavior remain unchanged; the agentic operator does not watch referenced Secrets or ConfigMaps.
 6. When `spec.ols.additionalCAConfigMapRef` is unset, the operator MUST omit `additional-ca-configmap`; the agentic operator then creates no additional-CA mount.
 7. When `spec.ols.tlsSecurityProfile` is unset, TLS for agentic provider egress MUST remain enabled. The operator MUST resolve the effective profile using the existing cluster API server fallback and operator default, then publish the resolved profile values. The agentic operator MUST pass those values through, and the sandbox MUST NOT select its own TLS profile defaults.

## Configuration Surface

| Field path | Description |
| --- | --- |
| `spec.ols.tlsConfig.keyCertSecretRef` | Secret with custom TLS cert/key (tls.crt, tls.key, optional ca.crt) |
| `spec.ols.additionalCAConfigMapRef` | ConfigMap with additional CA certificates for LLM provider connections |
| `spec.ols.mcpKubeServerConfig.caBundleRefs` | User CA bundle references augmenting shared MCP-process baseline trust |
| `spec.ols.tlsSecurityProfile` | OpenShift TLS security profile for API endpoints |
| `spec.ols.proxyConfig.proxyCACertificate` | ConfigMap ref + key for proxy CA certificate |
| `spec.llm.providers[].tlsSecurityProfile` | Per-provider TLS security profile for outgoing connections |

## Constraints

1. Service-ca certificates are only available on OpenShift clusters. The operator requires the OpenShift service-ca operator.
2. Custom TLS secrets must be in the operator's namespace (`openshift-lightspeed` by default).
3. PostgreSQL always uses SSL mode `require` with the service-ca certificate. This is not configurable.
4. The proxy CA certificate ConfigMap key is validated as a valid x509 PEM certificate during reconciliation.
